## Что такое KZGO Diagnostics?
Я начала с практического вопроса:
Как сократить время простоев горного оборудования и предотвратить аварии до того, как они произойдут?

Если параметры работы уже были измерены — они не должны теряться.
Если аномалия уже была обнаружена — система должна помнить её признаки.
Если диагноз уже был поставлен — он не должен ставиться заново с нуля.

Диагностика здесь — это не просто "сигнал тревоги". Это система, которая накапливает опыт:

Аномалии → становятся триггерами

Диагнозы → становятся шаблонами

Рекомендации → становятся инструкциями для операторов

# Архитектура: память, которая работает на опережение
# Ingestion Agent — сбор и валидация данных
Принимает телеметрию с датчиков (вибрация, температура, ток, давление, обороты).
Проверяет полноту и корректность данных. Сохраняет в InfluxDB.

## Anomaly Detection Agent — обнаружение отклонений
Проверяет каждый параметр по статическим порогам:

warning — предупреждение

critical — критическое значение

info — норма

Каждое отклонение фиксируется как Anomaly с привязкой к оборудованию, времени и параметру.

## Diagnosis Agent — интеллектуальная диагностика
На основе набора аномалий определяет:

Корневую причину (например, износ подшипника, перегрев, утечка)

Серьёзность (info / warning / critical)

Время до отказа (оценка)

Рекомендацию (действия для оператора или ремонтной службы)

Поддерживает два режима:

Rule-based — быстрая диагностика по шаблонам

# LLM-enhanced — если подключён OpenAI, система получает более точные и контекстные выводы

# Оркестрация на LangGraph
Все агенты объединены в единый Directed Acyclic Graph (DAG):

[Ingestion] → [Anomaly Detection] → (если есть аномалии) → [Diagnosis] → END
                                     ↓
                                (если нет) → END

# Режимы работы:

normal — штатная работа

warning — отклонения в пределах предупреждения

critical — критические значения

degrading — постепенное ухудшение параметров

Команды: start, stop, status, exit
